# Changelog — in progress

**Branch:** `main`

## 2026-07-26
- **What:** Added `docs/COMPONENT.md` (index + rule for component-specific dev guides under `docs/components/`) and linked it from `CLAUDE.md` under a new "Component development" section.
  **Why:** Requested by user: before building/modifying any reusable or component-kind-specific code, agents should check `docs/COMPONENT.md` first for any relevant convention doc (e.g. `docs/components/form.md`, `map.md`, `input.md`), and follow it if present.
- **What:** Added `docs/components/svg.md`, the first component guide, capturing conventions from the existing `AbstractSystemVisual` component (inline SVG only, no icon library/imported `.svg` assets, colors always via CSS design tokens, decorative `aria-hidden`, when to reuse the placeholder components instead of building a new SVG). Registered it in the `docs/COMPONENT.md` index table.
  **Why:** Requested by user as the first entry in the component-guide system just set up, so future SVG/graphics work follows the pattern already established rather than reinventing it.
- **What:** Installed `@svgr/webpack` and wired it up so `.svg` files can be imported as React components: `turbopack.rules` + `webpack` blocks in `next.config.ts` (Turbopack is the default bundler in Next 16, webpack rule is a `--webpack` fallback), and the ambient module declaration in `src/types/svg.d.ts`. Verified end-to-end with a temporary smoke-test route (import → `next build` → confirmed real `<svg>` markup with props merged in the prerendered HTML), then removed the scratch files. Updated `docs/components/svg.md` to document both the existing hand-written-inline-JSX pattern and the new imported-`.svg`-via-SVGR pattern (including the `currentColor` convention for file-based assets and the `src/assets/svg/` location for source files), and added a one-line pointer to it under "Stack" in `CLAUDE.md`.
  **Why:** Requested by user: "install svgr and all necessary setup." No `.svg`-as-component usage exists yet in the codebase (only hand-authored inline SVG so far), so this is forward-looking infra — the actual `src/assets/svg/` directory doesn't exist yet and will be created when the first real asset needs it.
- **What:** Found the one inline-SVG spot in the codebase (`AbstractSystemVisual`, the only file matching `<svg`) and extracted its static shapes (grid pattern, panels, connection lines, nodes, corner marks) into `src/assets/svg/system-diagram.svg`, imported via the new SVGR setup. The page-varying `label` prop (different text on the homepage hero vs. the enterprise-platforms page) stays as JSX — a static file can't take props — now rendered as an absolutely-positioned `MicroLabel`, which makes it styleable with ordinary Tailwind classes instead of the previous raw SVG `fontSize`/`letterSpacing` attributes. Verified pixel-for-pixel equivalent output (same coordinates/colors/opacities, SVGO's `<rect>`→`<path>` conversion is visually identical) via `next build` + a running dev server, checking the rendered HTML directly. Rewrote `docs/components/svg.md` around imported-`.svg`-via-SVGR as the default pattern, with a new "hybrid" section documenting the graphic-import + JSX-overlay approach `AbstractSystemVisual` now uses, and a note on the (pre-existing, not introduced by this change) duplicate-`id`-across-instances behavior when the same SVG asset is used twice on one page.
  **Why:** Requested by user: find every SVG in the site, extract to files in one shared folder, import instead, and make it Tailwind-customizable. `AbstractSystemVisual` was the only inline SVG in the codebase.
